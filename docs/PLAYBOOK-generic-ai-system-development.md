# AI 系统开发手册（通用版）— Development Playbook for Complex AI Systems

> 一份从真实复杂 AI 系统项目（某「家庭门前风险感知系统」）中提炼、可复用于 **所有** 复杂 AI 系统的开发手册。
> 原项目是参赛型 Demo，但下列原则与具体技术栈、具体业务无关，可原样套用到任何「感知 → 判断 → 行动」类 AI 系统。
>
> 本手册是**纯原则版**：已去除所有项目专有名词（模块名 / PR 号 / 阶段代号 / 配置项），只保留可迁移的工程 / 产品 / Demo 原则。
> 每个原则按「当初假设 → 验证结果 → 关键证据 → 如何迁移」组织。
> 来源：某系统 全链路研发 + MVP Release Candidate + 真实端到端验证（全断言通过）。

---

## 如何使用本手册

- **第一部分**：你**一开始就该坚持**的原则（已被验证正确）。
- **第二部分**：你**走到后半程才会懂**的原则（验证阶段新增，最值钱）。
- **第三部分**：你**会本能想做、但必须忍住**的诱惑（被证伪的想法）。
- **第四部分**：把以上浓缩成的**七阶段开发流程**（下一代可直接套用）。

---

## 一、被验证正确的原则

### 1. 先事实层，再展示层

**原则**：在动手任何 UI / 演示 / 可视化之前，先把「系统到底看到了什么事实」做稳。事实层（原始结构化事实）必须独立于展示层（人类可读的叙事）存在。

**当初的约束**：
```
事实层（检测 / 跟踪 / 事件 / 特征 / 规则 / 决策 / 行动）
        ↓ 稳定后
展示层（Dashboard / 风险卡 / 行为时间线 / 多角色视图）
```

**验证结果**：正确。

**关键证据**：项目后半程暴露的大部分问题——时间线空白、风险卡闪烁、多端页面无内容——**本质全是展示层问题**。而事实层（核心感知流水线）一旦在事实层阶段稳定，就再没动摇过。最后靠真实端到端验证证明：事实层能确定性产出高风险闭环。

**如何迁移**：新 AI 系统起步时，把「能输出稳定事实」当作第一个里程碑，而不是「能画出一个好看的界面」。展示层的 bug 成本低、事实层的 bug 成本极高；顺序反了，你会用大量返工为展示层的不稳定买单。

---

### 2. 冻结边界优于快速修改

**原则**：核心系统（被多模块依赖的「事实生产器」）一旦稳定，就冻结其对外契约；上层消费方只能通过白名单 / 只读接口消费，不得反向改核心。

**当初的约束**：
```
核心事实层（感知内核）  —— 冻结（契约 / Schema / 接口稳定）
        ↓ 消费（白名单 + 只读）
展示层 / 演示层         —— 可自由变化
```

**验证结果**：正确。

**关键证据**：在冻结之后，展示层经历了剧烈变化——Dashboard 生命周期、多角色视图、真实视频输入、WS 状态快照、Session 管理……**全部改动都发生在展示层，核心感知系统一行没动**。冻结边界（白名单 + 契约测试）让「换展示不碰核心」成为现实。加多视图时，零新增后端契约、零新增对核心的 import，契约测试全程不破。

**如何迁移**：任何会被多处消费的「事实源」都要尽早冻结边界，用契约测试守住。否则每一次上层需求变动都会腐蚀核心，最终不可维护。冻结不是僵化，是让变化发生在正确的层。

---

### 3. E2E 优于单元测试（功能完成 ≠ 集成完成）

**原则**：单元测试全绿只证明「每个零件对」，不证明「系统能跑通」。复杂 AI 系统必须有真实端到端的验证：真实组件组装、真实协议、真实数据流。

**当初的假设**：单元测试全绿 ≈ 系统正常。

**验证结果**：错误。

**关键证据**：真实端到端验证（网关 → WS → 状态回写 全链路，非 mock）一次性暴露了三个集成级缺陷，单元测试一个都没抓到：
1. **某次功能交付未进入运行链路** → 关键配置为 null、无规则覆盖 → 初期高风险事件 = 0（事实层其实没接到展示路径）；
2. **帧率快进破坏规则** → 自写场景误设抽帧参数 = 0，重入间隔被拉宽超过时间窗口 → 窗口内访问次数永远 = 1 → 不出高风险；
3. **演示状态存储首见状态覆盖** → 首见事件被强制置为 pending，单次点击确认被静默丢弃。

**新增原则**：**功能完成 ≠ 集成完成**。零件对 ≠ 系统对。

**如何迁移**：AI 系统（尤其多组件、有状态、有实时流的）必须在交付前跑一次「真实组装 + 真实协议」的 E2E。mock 能证明接口对齐，证明不了闭环成立。

---

## 二、验证阶段新增原则（最值钱的部分）

> 这些原则在项目开始时根本不知道，是走到验证阶段才被「打脸」式学到的。

### 4. Demo 不只是展示 —— Demo 是第一个产品入口

**当初的理解**：Demo = 一个 UI，用来给评委 / 客户看。

**后来的发现**：错误。

**正确理解**：Demo = 第一个产品入口。它是真实用户（评委 / 客户）第一次「使用」系统的地方，因此它必须具备产品级能力：

由此才自然催生出原本「只是展示」不会想到的需求：
- **真实输入上传**（真实输入，而非硬编码样例）
- **生命周期管理**（启动 / 运行 / 停止 / 重置）
- **状态快照**（刷新不丢上下文）
- **Session 管理**（多会话隔离）

**关键证据**：正是把 Demo 当作「产品入口」而非「幻灯片」，才推动了真实视频输入 + 生命周期、`reset` 接口、WS snapshot 等原本属于「产品」才有的能力。

**如何迁移**：从第一天就把 Demo 当产品入口设计。它的稳定性、状态管理、输入灵活性，决定了别人对你的系统的第一印象和信任度。

---

### 5. 评审关心闭环，不关心页面数量

**当初容易陷入**：摄像头端 / 老人端 / 家属端 / 社区端……四五个页面，看起来「覆盖全」。

**后来的验证发现**：评审真正关注的不是「你做了几个端」，而是：
```
发现 → 确认 → 处置 → 闭环
```
他们不关心你用哪套前端框架，不关心登录 / 用户体系，只关心**一条风险事实能否被发现、被解释、被处理、形成闭环**。

**最终收敛**：把「多端」收敛成「单界面多视图」（阶段叙事，不是角色）：
- ① 风险发现
- ② 相关方确认
- ③ 处置方处置

一个 `事件 ID` 流过多个视图 = 一个事实被多角色共享。

**关键证据**：范围收敛决策把「多端闭环 / 多端开发」改为「多角色协同闭环模拟」，从「多个独立产品」改为「单界面多视图共享同一状态」。评审三问（系统理解行为？风险有解释？发现后产生行动？）全部落在一条故事线上。

**如何迁移**：做演示 / 产品时，用「闭环故事线」替代「功能清单」。能讲通一条端到端闭环，胜过十个孤立页面。

---

### 6. 稳定高风险比新增功能重要

**验证阶段的发现**：如果系统只能产生低风险事件，那么页面再漂亮、功能再多，**故事也讲不通**——因为低风险没有行动、没有闭环、没有叙事。

**于是**：稳定核心高风险闭环（能确定性产出 HIGH 的那一步）的优先级**超过**了多端页面、视频上传、流媒体接入等所有「看起来更重要」的功能。事实层不出高风险 → 上层全是空壳。

**关键证据**：通过调阈值（如重复访问阈值 3→2）+ 相关方联系配置，让夜间摄像头场景确定性产出完整高风险闭环（高风险 → 通知相关方 → 生成处置任务 → 闭环）。这是「最难的事实层稳定」问题，也是整个演示成立的基石。

**新增经验**：**先有能稳定复现的核心故事，再做展示打磨**。一个能稳定复现的高风险，比十个漂亮但空洞的页面值钱。

**如何迁移**：任何 AI 系统，先问「我最核心的那条故事，能确定性复现吗？」不能，就停下所有周边功能，先把核心故事钉死。

---

### 7. 系统验证优于功能验证（Functionally Correct ≠ Operationally Correct）

**当初的假设**：功能都在、模块都绿 ≈ 系统正确。

**验证结果**：错误。所有功能存在、所有模块正常，但**整个系统的运行状态不正确**——这是典型的「功能正确 ≠ 系统正确」。

**关键证据**：验证阶段暴露的运行态缺陷，每一例都是「功能齐全却运行态错误」：
- 状态映射表（告警表）闪烁（告警在视图间跳变）
- 行为时间线空白（事实有、展示空）
- 高风险不出现（链路通、故事断）
- 处理流水线循环后失效（单轮对、多轮崩）
- 晚连接看不到历史（连上了、上下文丢了）

后续大量时间其实花在：**长时间运行 / 多轮循环 / 输入切换 / 晚连接 / 状态恢复**——这些都属于**运行态验证（Operational Validation）**，是 AI 项目最易遗漏的一层。

**新增原则**：AI 系统必须验证**长期运行状态**，而不仅是功能是否存在。

**如何迁移**：功能正确性靠单测 / 单轮 E2E 可证；运行态正确性只能靠「长时间跑 + 多轮 + 切换 + 晚连接 + 重置恢复」验证。把运行态验证列为交付前必做项，而非「跑通一次就算完」。

> 本原则是原则 3（E2E 优于单元测试）的进一步下沉：E2E 验证「能否跑通」，系统验证验证「能否长期正确运行」。两者递进，缺一不可。

---

### 8. 真实数据比模型能力更重要

**当初的迷思**：Demo 成败取决于模型准确率——检测 / 跟踪模型够不够强、规则 / 复合规则 / 高风险判定够不够准。

**验证结果**：错误。真正让 Demo 成立的转折点是**接入一段真实场景视频**；后续扩展到更多真实场景（A 类 / B 类 / 合成视频），验证的是「系统能否消费真实世界数据」，不是「模型是否更强」。

**关键证据**：没有真实输入，生命周期问题、输入切换问题、状态污染、高风险故事**全都无法暴露或验证**。真实数据一接入，系统问题才被逼出来。项目定位也从「视频分析 Demo」升级为「**风险感知系统 Demo**」——区别在于后者有完整闭环。

**新增原则**：**真实数据会暴露系统问题，Mock 数据只会隐藏系统问题。**

**如何迁移**：任何 AI 系统，优先拿到一段真实场景数据跑起来，再谈模型增强。用 Mock 自检接口可以，但**不能用 Mock 证明系统成立**。Demo 成败首先取决于有没有真实输入，其次才是模型。

---

### 9. 先固定故事，再提高泛化

**当初的本能**：把某阈值从 N 调到 N−1（如重复判定阈值 3→2）是「过拟合」，该避免。

**验证结果**：错误。Demo 阶段恰恰**应该**这么做——此阶段目标不是「证明对所有场景有效」，而是「证明在一个场景上成立」。这是两个完全不同的问题。

**关键证据**：实际遵循的顺序是 **单场景成立 → 多场景成立 → 泛化成立**：场景 A → 高风险、场景 B → 低风险，本身就是最小对照实验。稳定核心高风险阶段正是通过固定一个场景确定性产出高风险，才让整个 Demo 成立。

**新增原则**：**Demo 阶段允许对故事过拟合，但必须明确记录过拟合点，为后续泛化预留出口。**

**如何迁移**：研发顺序不能跳过单场景直接追求泛化。先把一个故事钉死（记录你调了哪些阈值、哪些场景被临时排除），再扩展场景，最后才谈泛化。过拟合点就是未来的泛化工作项。

---

### 10. 状态是一等公民

**当初的关注**：检测 / 跟踪 / 规则——模型与规则。

**验证结果**：最大的 Bug 来自**状态**。例如告警映射表 / 指令映射表 / 行为映射表 / 会话 / 快照 / 循环计数 / 重置。它们不是 AI，却决定系统能否**持续运行**。

**关键证据**：运行时生命周期决策（ADR）固化了状态管理边界；多轮循环 / 晚连接 / 重置暴露的几乎全是状态类缺陷。很多 AI 项目最后失败不是模型不行，而是**状态管理崩了**。

**新增原则**：**当系统开始跨时间运行时，状态管理的重要性会超过模型本身。**

**如何迁移**：把状态（映射表 / 会话 / 快照 / 循环计数 / 重置语义）当作与模型同等的一等公民——设计、测试、冻结。状态层要有独立的可验证契约，不能散落在各模块的临时变量里。

---

### 11. 每个阶段都必须产生可验证资产

**当初的习惯（隐性）**：做完功能就进下一阶段，「相信它应该对」。

**验证结果**：错误。每个阶段都留下「能证明它对」的资产，没有「相信它应该对」。

**关键证据**（每阶段都产出可重复验证的证据）：
- 跟踪模块 → 产出事实事件（结构化，可断言）
- 规则引擎 → 产出风险事件（可断言）
- 决策模块 → 产出动作指令（可断言）
- 展示层 → 产出可视化证据（人话风险卡 + 行为时间线）
- 验证阶段 → 产出端到端验证报告（全断言通过）

**新增原则**：**每完成一个阶段，都必须留下一个可重复验证的证据资产（测试 / 报告 / 脚本 / Demo / 契约），否则该阶段视为未完成。**

**如何迁移**：把「资产交付」作为阶段完成的定义。没有可重复验证证据的阶段 = 未完成，不允许进入下一阶段。这能把「我以为对了」变成「我能证明对了」。

## 三、被证伪的想法（避免重蹈覆辙）

> 这些是「本能想做、但被证明是坑」的诱惑。记下来，下次直接跳过。

### 被证伪 1：先把页面做出来，后面再接数据

**诱惑**：UI 见效快、容易演示，先堆页面，数据以后接。

**结果**：大量返工。

**对照教训**：走「事实层优先」路线的项目，展示层出现的问题（时间线空白、风险卡闪烁）都是**廉价的可视化 bug**，而非事实缺失。反证：一旦展示层试图消费「还没准备好的数据」（如早期直接读墙钟时间而非模拟时钟），立刻出现对不上的叙事——这说明任何「页面先于数据」的苗头都会制造空白 / 闪烁 UI。

**教训**：页面可以后做，但页面依赖的**事实必须先在**。永远不要让 UI 成为系统的第一块基石。

---

### 被证伪 2：视频上传 = 项目价值

**诱惑**：能上传视频、能播视频，看起来就很「完成」。

**结果**：上传只是入口，不是价值。

**正确理解**：视频上传是**输入的搬运工**。真正的价值链条是：
```
行为理解 → 风险升级 → 闭环处理
```
视频进来了，如果系统不理解「谁、停留多久、重复几次、夜间与否」，上传毫无意义。

**关键证据**：验证中，视频能跑、帧能抽，但抽帧参数误设导致快进破坏重复检测 → 不出高风险 → 整个演示空壳。证明「能播视频」和「能产生风险闭环」是两回事。项目定位也从「视频分析 Demo」升级为「**风险感知系统 Demo**」——区别在于后者有完整闭环。

**教训**：把「能接收输入」和「能产生价值」分开。价值在闭环，不在入口。

---

### 被证伪 3：多角色 = 多个系统

**诱惑**：家属要一个端、社区要一个端、老人要一个端 → 干脆做三个独立产品 / App / Web。

**结果**：进入新产品工程，不验证核心价值，且多端硬编码接口导致后续接入痛苦。

**正确理解**：正确模式是**一个事实源 → 多个消费视角**：
```
单一事实源（聚合状态）
        ↓ 投影
视图 A（风险发现）/ 视图 B（相关方确认）/ 视图 C（处置方处置）
```
新增一个消费者 ≈ 加一个视图，零成本；而不是加一套系统。

**关键证据**：固化「多视图共享同一 state，切换不重连 / 不重订实时通道」。早期契约测试 / 接口冻结的回报在此兑现：一个事件被多角色消费者共享，是「一个事实源 + 角色视图投影」的自然结果。

**教训**：多角色需求 ≠ 多系统需求。先冻结事实源，再用视图投影满足多角色，避免重复建设和接口碎片化。

---

## 四、下一代开发流程（七阶段）

> 把以上全部浓缩成一个可直接套用的流程。**原项目实际走过的路，就是这个流程。**

### Stage 0 · 问题定义
- **目标**：定义系统「是什么」**和「不是什么」**。
- **关键纪律**：边界（不做什么）比功能（做什么）更先定义。边界错了，后面全歪。
- **常见陷阱**：跳过边界定义，直接堆功能。

### Stage 1 · 事实层
- **目标**：系统能稳定输出「它看到了什么事实」（结构化、无业务判断）。
- **关键纪律**：事实层字段**禁止**夹带业务判断。事实是「有人在门口停留 X 秒」，不是「这是嫌疑人」。
- **常见陷阱**：在事实层就急着打风险标签。

### Stage 2 · 规则层
- **目标**：在事实之上做「被测量的数值」（特征）和「规则语义」（风险）。
- **关键纪律**：特征层与规则层分离；规则消费特征，不回头读事实；风险评分 = 规则命中强度，不是概率。
- **常见陷阱**：阈值一变就改事实层。

### Stage 3 · 动作层
- **目标**：风险语义翻译成可执行动作，并路由到正确接收方。
- **关键纪律**：动作层只翻译，不重新判断；路由规则可配置。
- **常见陷阱**：动作层偷偷再做一次风险决策。

### Stage 4 · 闭环验证（最关键的分水岭）
- **目标**：把以上四层**真实组装**，跑通端到端闭环，并**确定性复现核心故事**。
- **关键纪律**：**功能完成 ≠ 集成完成**。必须 E2E 验证；核心故事（稳定高风险闭环）钉死前，不做任何周边功能。
- **常见陷阱**：靠单元测试断定系统正常；核心故事靠运气而非确定性。

### Stage 5 · 展示层
- **目标**：把事实 / 风险 / 时间线，变成人类可读的叙事。
- **关键纪律**：展示层消费冻结边界（白名单 + 只读），不得反向改核心。
- **常见陷阱**：展示层直接改核心模型来「方便显示」。

### Stage 6 · 演示层
- **目标**：把系统变成「第一个产品入口」——可输入、可管理、可重置、状态不丢。
- **关键纪律**：用「闭环故事线」替代「功能清单」；评审关心闭环不关心页面数；Demo = 产品入口（生命周期 / 快照 / Session）。
- **常见陷阱**：堆页面数量；把 Demo 当幻灯片。

### Stage 7 · 产品化（知道何时停）
- **目标**：达到「首看者 5 分钟内理解价值」即停，进入产品化评估。
- **关键纪律**：**停止纪律**——演示级里程碑达成后，下一个里程碑是「让人理解价值」，不是「再加技术」。过度建设是另一种失败。
- **常见陷阱**：在 Demo 成功后无边界地扩张（做 App / 登录 / 用户体系），偏离核心价值验证。

### 贯穿七阶段的纪律
- **资产交付（见原则 11）**：每个 Stage 收尾都必须留下可重复验证的证据资产（测试 / 报告 / 脚本 / Demo / 契约），否则该 Stage 视为未完成。
- **运行态验证（见原则 7）**：从 Stage 4 起，必须以「长时间运行 + 多轮循环 + 输入切换 + 晚连接 + 重置恢复」验证系统，而非只验功能存在。
- **状态一等公民（见原则 10）**：跨时间运行后，状态边界（映射表 / 会话 / 快照 / 循环计数 / 重置）的优先级超过模型本身，须有独立可验证契约。
- **真实输入优先（见原则 8）**：Stage 1 起就接入真实数据跑起来，Mock 只用于自检接口，不能用来证明系统成立。
- **先固定故事再泛化（见原则 9）**：研发顺序 单场景成立 → 多场景成立 → 泛化成立，不得跳过前两步直接追求泛化；Demo 阶段允许对故事过拟合，但须记录过拟合点。

---

## 核心一句话

> **不要先证明系统很强，而要先证明系统是真的；不要先追求泛化，而要先建立一个能够稳定复现、可验证、可闭环的事实系统。**

（推论：先让事实稳，再让闭环通，最后让故事好看；冻结核心、投影视图、E2E 验证、懂得停下。）
