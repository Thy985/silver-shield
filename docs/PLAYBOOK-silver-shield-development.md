# Silver Shield Development Playbook（银龄盾开发手册）

> 一份从 **SilverShield（银龄盾）** 项目中提炼、可复用于 **所有复杂 AI 系统** 的开发手册。
>
> 它不是「银龄盾开发了什么」的功能清单，而是「银龄盾**验证**了哪些工程 / 产品 / Demo 原则」。
> 每个原则都来自真实的踩坑与真实的验证，按「当初假设 → 验证结果 → 关键证据 → 如何迁移」组织。
>
> 本手册自包含、可脱离本项目使用。来源：SilverShield P0-1~P0-11 全链路 + MVP Release Candidate（`v0.1.0-mvp-rc`，2026-07-20）+ 真实端到端验证（12/12）。

---

## 如何使用本手册

- **第一部分**：你**一开始就该坚持**的原则（已被验证正确）。
- **第二部分**：你**走到后半程才会懂**的原则（验证阶段新增，最值钱）。
- **第三部分**：你**会本能想做、但必须忍住**的诱惑（被证伪的想法）。
- **第四部分**：把以上浓缩成的**七阶段开发流程**（下一代可直接套用）。

---

## 一、被验证正确的原则

### 1. 先事实层，再展示层

**原则**：在动手任何 UI / 演示 / 可视化之前，先把「系统到底看到了什么事实」做稳。事实层（原始结构化事实）必须独立于展示层（人类可读的叙事）存在。

**当初的约束**：
```
事实层（检测 / 跟踪 / 事件 / 特征 / 规则 / 决策 / 行动）
        ↓ 稳定后
展示层（Dashboard / 风险卡 / 行为时间线 / 多角色视图）
```

**验证结果**：正确。

**关键证据**：项目后半程暴露的大部分问题——时间线空白、风险卡闪烁、三端页面无内容——**本质全是展示层问题**。而事实层（7 层感知流水线）一旦在 P0-3~P0-10 稳定，就再没动摇过。最后靠真实端到端验证证明：事实层能确定性产出 HIGH 闭环。

**如何迁移**：新 AI 系统起步时，把「能输出稳定事实」当作第一个里程碑，而不是「能画出一个好看的界面」。展示层的 bug 成本低、事实层的 bug 成本极高；顺序反了，你会用大量返工为展示层的不稳定买单。

---

### 2. 冻结边界优于快速修改

**原则**：核心系统（被多模块依赖的「事实生产器」）一旦稳定，就冻结其对外契约；上层消费方只能通过白名单 / 只读接口消费，不得反向改核心。

**当初的约束**：
```
home_perception  —— 冻结（契约 / Schema / 接口稳定）
        ↓ 消费（白名单 + 只读）
silver_demo      —— 可自由变化
```

**验证结果**：正确。

**关键证据**：在冻结之后，展示层经历了剧烈变化——Dashboard 生命周期、三角色视图、真实视频输入、WS 状态快照、Session 管理……**全部改动都发生在 `silver_demo`，核心感知系统一行没动**。ADR-0015 的冻结边界（白名单 + 契约测试）让「换展示不碰核心」成为现实。P0-11.4 加三视图时，零新增后端契约、零新增对 `home_perception` 的 import，`freeze_boundary` 测试全程不破。

**如何迁移**：任何会被多处消费的「事实源」都要尽早冻结边界，用契约测试守住。否则每一次上层需求变动都会腐蚀核心，最终不可维护。冻结不是僵化，是让变化发生在正确的层。

---

### 3. E2E 优于单元测试（功能完成 ≠ 集成完成）

**原则**：单元测试全绿只证明「每个零件对」，不证明「系统能跑通」。复杂 AI 系统必须有真实端到端的验证：真实组件组装、真实协议、真实数据流。

**当初的假设**：`pytest` 全绿 ≈ 系统正常。

**验证结果**：错误。

**关键证据**：真实端到端验证（网关 → WS → 状态回写 全链路，非 mock）一次性暴露了三个集成级缺陷，单元测试一个都没抓到：
1. **PR #50 未进入运行链路** → `family_contact=null`、无 `rule_override` → 初期 HIGH=0（事实层其实没接到 demo 路径）；
2. **fps 快进破坏规则** → 自写场景误设 `fps_target=0`，重入间隔被拉宽超过 `frequency_window` → `visits_in_window` 永远 = 1 → 不出 HIGH；
3. **DemoStateStore 首见状态覆盖** → 首见 warning 被强制 `pending`，单次点击确认被静默丢弃。

**新增原则**：**功能完成 ≠ 集成完成**。零件对 ≠ 系统对。

**如何迁移**：AI 系统（尤其多组件、有状态、有实时流的）必须在交付前跑一次「真实组装 + 真实协议」的 E2E。mock 能证明接口对齐，证明不了闭环成立。

## 二、验证阶段新增原则（最值钱的部分）

> 这些原则在项目开始时根本不知道，是走到 P0-11 验证阶段才被「打脸」式学到的。

### 4. Demo 不只是展示 —— Demo 是第一个产品入口

**当初的理解**：Demo = 一个 UI，用来给评委看。

**后来的发现**：错误。

**正确理解**：Demo = 第一个产品入口。它是真实用户（评委 / 客户）第一次「使用」系统的地方，因此它必须具备产品级能力：

由此才自然催生出原本「只是展示」不会想到的需求：
- **视频上传**（真实输入，而非硬编码样例）
- **生命周期管理**（启动 / 运行 / 停止 / 重置）
- **状态快照**（刷新不丢上下文）
- **Session 管理**（多会话隔离）

**关键证据**：正是把 Demo 当作「产品入口」而非「幻灯片」，才推动了 P0-11.2 真实视频输入 + 生命周期、`POST /demo/reset`、WS snapshot 等原本属于「产品」才有的能力。

**如何迁移**：从第一天就把 Demo 当产品入口设计。它的稳定性、状态管理、输入灵活性，决定了别人对你的系统的第一印象和信任度。

---

### 5. 评委关心闭环，不关心页面数量

**当初容易陷入**：摄像头端 / 老人端 / 家属端 / 社区端……四五个页面，看起来「覆盖全」。

**后来的验证发现**：评委真正关注的不是「你做了几个端」，而是：
```
发现 → 确认 → 处置 → 闭环
```
他们不关心你用 React 还是 Vue，不关心登录 / 用户体系，只关心**一条风险事实能否被发现、被解释、被处理、形成闭环**。

**最终收敛**：把「多端」收敛成「单 Dashboard 三视图」（阶段叙事，不是角色）：
- ① 风险发现
- ② 家属确认
- ③ 社区处置

一个 `warning_id` 流过三个视图 = 一个事实被多角色共享。

**关键证据**：ADR-0017 的范围收敛。把「三端闭环 / 三端开发」改为「多角色协同闭环模拟」，从「三个独立产品」改为「单 Dashboard 三视图共享同一状态」。评委三问（AI 理解行为？风险有解释？发现后产生行动？）全部落在一条故事线上。

**如何迁移**：做演示 / 产品时，用「闭环故事线」替代「功能清单」。能讲通一条端到端闭环，胜过十个孤立页面。

---

### 6. 稳定 HIGH 比新增功能重要

**验证阶段的发现**：如果系统只能产生 LOW 风险，那么页面再漂亮、功能再多，**故事也讲不通**——因为 LOW 风险没有行动、没有闭环、没有叙事。

**于是**：P0-11.5a（稳定 HIGH 闭环）的优先级**超过**了三端页面、视频上传、RTSP 等所有「看起来更重要」的功能。事实层不出 HIGH → 上层全是空壳。

**关键证据**：P0-11.5a 通过调阈值（如 `repeat_visit_count` 3→2）+ `family_contact` 配置，让夜间 CCTV 场景确定性产出完整 HIGH 闭环（HIGH → 通知家属 → 生成社区任务 → 闭环）。这是 PR #50 解决的「最难的事实层稳定」问题，也是整个 Demo 成立的基石。

**新增经验**：**先有能稳定复现的核心故事，再做展示打磨**。一个能稳定复现的 HIGH，比十个漂亮但空洞的页面值钱。

**如何迁移**：任何 AI 系统，先问「我最核心的那条故事，能确定性复现吗？」不能，就停下所有周边功能，先把核心故事钉死。

## 三、被证伪的想法（避免重蹈覆辙）

> 这些是「本能想做、但被证明是坑」的诱惑。记下来，下次直接跳过。

### 被证伪 1：先把页面做出来，后面再接数据

**诱惑**：UI 见效快、容易演示，先堆页面，数据以后接。

**结果**：大量返工。

**SilverShield 的对照**：我们走了「事实层优先」（P0-3~P0-10 再 P0-11），因此展示层出现的问题（时间线空白、风险卡闪烁）都是**廉价的可视化 bug**，而非事实缺失。反证：一旦展示层试图消费「还没准备好的数据」（如早期 dashboard 直接读墙钟 `created_at` 而非模拟时钟 `demo_time`），立刻出现对不上的叙事——这说明任何「页面先于数据」的苗头都会制造空白 / 闪烁 UI。

**教训**：页面可以后做，但页面依赖的**事实必须先在**。永远不要让 UI 成为系统的第一块基石。

---

### 被证伪 2：视频上传 = 项目价值

**诱惑**：能上传视频、能播视频，看起来就很「完成」。

**结果**：上传只是入口，不是价值。

**正确理解**：视频上传是**输入的搬运工**。真正的价值链条是：
```
行为理解 → 风险升级 → 闭环处理
```
视频进来了，如果系统不理解「谁、停留多久、重复几次、夜间与否」，上传毫无意义。

**关键证据**：E2E 验证中，视频能跑、帧能抽，但 `fps_target=0` 快进破坏 repeat 检测 → 不出 HIGH → 整个演示空壳。证明「能播视频」和「能产生风险闭环」是两回事。项目定位也从「视频 AI 分析 Demo」升级为「**风险感知系统 Demo**」——区别在于后者有完整闭环。

**教训**：把「能接收输入」和「能产生价值」分开。价值在闭环，不在入口。

---

### 被证伪 3：多角色 = 多个系统

**诱惑**：家属要一个端、社区要一个端、老人要一个端 → 干脆做三个独立产品 / App / Web。

**结果**：进入新产品工程，不验证核心价值，且多端硬编码接口导致后续接入痛苦。

**正确理解**：正确模式是**一个事实源 → 多个消费视角**：
```
单一事实源（DemoAggregateState）
        ↓ 投影
视图 A（风险发现）/ 视图 B（家属确认）/ 视图 C（社区处置）
```
新增一个消费者 ≈ 加一个视图，零成本；而不是加一套系统。

**关键证据**：ADR-0017 固化「三视图共享同一 state，切换不重连 / 不重订 WS」。早期 ABC / Schema / Contract Test 的回报在此兑现：一个事件被多角色消费者共享，是「一个事实源 + 角色视图投影」的自然结果。

**教训**：多角色需求 ≠ 多系统需求。先冻结事实源，再用视图投影满足多角色，避免重复建设和接口碎片化。

## 四、下一代开发流程（七阶段）

> 把以上全部浓缩成一个可直接套用的流程。**SilverShield 实际走过的路，就是这个流程。**

### Stage 0 · 问题定义
- **目标**：定义系统「是什么」**和「不是什么」**。
- **SilverShield 对应**：模块边界铁律——「只输出标签 / 事件，绝不输出诈骗判定；是否诈骗由中心决定」。
- **关键纪律**：边界（不做什么）比功能（做什么）更先定义。边界错了，后面全歪。
- **常见陷阱**：跳过边界定义，直接堆功能。

### Stage 1 · 事实层
- **目标**：系统能稳定输出「它看到了什么事实」（结构化、无业务判断）。
- **SilverShield 对应**：P0-3 检测 / P0-5 跟踪 / P0-6 VisitorEvent（事实事件层，不含 `risk_level` / `score`）。
- **关键纪律**：事实层字段**禁止**夹带业务判断（见 ADR-0007）。事实是「有人在门口停留 X 秒」，不是「这是嫌疑人」。
- **常见陷阱**：在事实层就急着打风险标签。

### Stage 2 · 规则层
- **目标**：在事实之上做「被测量的数值」（特征）和「规则语义」（风险）。
- **SilverShield 对应**：P0-7a 特征提取（数值，非判断）/ P0-7b 规则引擎（`score` = 规则命中强度，不是诈骗概率）。
- **关键纪律**：特征层与规则层分离；规则消费特征，不回头读事实（ADR-0005 契约稳定）。
- **常见陷阱**：阈值一变就改事实层。

### Stage 3 · 动作层
- **目标**：风险语义翻译成可执行动作，并路由到正确接收方。
- **SilverShield 对应**：P0-8/9 决策 + 行动 + main 装配；Dispatcher 1:1 路由（`ESCALATE_COMMUNITY` → 社区任务；`family_contact` 非空 → 家属消息）。
- **关键纪律**：动作层只翻译，不重新判断；路由规则可配置。
- **常见陷阱**：动作层偷偷再做一次风险决策。

### Stage 4 · 闭环验证（最关键的分水岭）
- **目标**：把以上四层**真实组装**，跑通端到端闭环，并**确定性复现核心故事**。
- **SilverShield 对应**：P0-11.5a 稳定 HIGH + 真实 E2E（网关 → WS → 状态回写）12/12。
- **关键纪律**：**功能完成 ≠ 集成完成**。必须 E2E 验证；核心故事（稳定 HIGH 闭环）钉死前，不做任何周边功能。
- **常见陷阱**：靠单元测试断定系统正常；核心故事靠运气而非确定性。

### Stage 5 · 展示层
- **目标**：把事实 / 风险 / 时间线，变成人类可读的叙事。
- **SilverShield 对应**：P0-11.3 风险解释层（人话原因 `reason_summary` + 规则强度 + 行为时间线）。
- **关键纪律**：展示层消费冻结边界（白名单 + 只读），不得反向改核心。
- **常见陷阱**：展示层直接改核心模型来「方便显示」。

### Stage 6 · 演示层
- **目标**：把系统变成「第一个产品入口」——可输入、可管理、可重置、状态不丢。
- **SilverShield 对应**：P0-11.4 三视图 Tab + P0-11.5b 5 分钟剧本（口播 + 切 Tab + 点按钮全固定）。
- **关键纪律**：用「闭环故事线」替代「功能清单」；评委关心闭环不关心页面数；Demo = 产品入口（生命周期 / 快照 / Session）。
- **常见陷阱**：堆页面数量；把 Demo 当幻灯片。

### Stage 7 · 产品化（知道何时停）
- **目标**：达到「首看者 5 分钟内理解价值」即停，进入产品化评估。
- **SilverShield 对应**：RC tag `v0.1.0-mvp-rc` 已打；停止纪律（不扩 App / ReID / RTSP / voice）；后续增强归 v2/P1。
- **关键纪律**：**停止纪律**——演示级里程碑达成后，下一个里程碑是「让人理解价值」，不是「再加技术」。过度建设是另一种失败。
- **常见陷阱**：在 Demo 成功后无边界地扩张（做 App / 登录 / 用户体系），偏离核心价值验证。

---

## 核心一句话

> **先让事实稳，再让闭环通，最后让故事好看；冻结核心、投影视图、E2E 验证、懂得停下。**
