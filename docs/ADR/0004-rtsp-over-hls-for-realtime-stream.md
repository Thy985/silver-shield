# ADR-0004: 实时取流 RTSP 优先、HLS 回退

- 状态：Accepted
- 日期：2026-07-18
- 决策者：Owner
- 相关：`docs/02_architecture.md` §2.5、`src/home_perception/ingestion/`、`config/default.yaml`

## 背景（Context）

Home 感知模块基于萤石（EZVIZ）摄像头取流。萤石平台同时支持 RTSP（protocol=1）与 HLS（protocol=2）。
项目早期在 `prototypes/` 中验证的是 **HLS**（切片式、对防火墙友好、易在浏览器/网页侧回放）。

但门前感知的核心价值是**低延迟前置预警**——把防护时间前移到"踩点/重复来访"阶段。
HLS 基于分段切片，天然引入秒级缓冲延迟，与"实时"目标冲突。

## 决策（Decision）

**实时感知取流默认使用 RTSP（protocol=1）以降低端到端延迟；HLS（protocol=2）作为回退方案。**

- 主路径：RTSP，追求最低端到端延迟。
- 回退：当 RTSP 不可用（网络策略限制、平台限制、连接不稳定）时切换 HLS，保证可用性。
- 抽帧控算力：无论哪种协议，取流后按 `config.ingestion.fps_target=8` 抽帧再送检测（见 ADR-0003）。

## 动机（Rationale）

- **延迟决定预警价值**：踩点/蹲守识别对时效敏感，HLS 切片延迟会显著削弱前置预警的意义。
- **回退保可用**：RTSP 在部分家庭网络/防火墙下可能受限，保留 HLS 回退避免"取不到流"的单点失败。
- **不推翻原型积累**：`prototypes/` 的 HLS 验证成果不作废，转为回退路径，价值仍在。

## 后果（Consequences）

- ✅ 端到端延迟显著低于 HLS，满足实时预警底线。
- ✅ 双协议冗余：主路径失败可回退，鲁棒性更好。
- ⚠️ RTSP 在某些网络环境需要额外的连接/重连处理（`ingestion` 层的取流重连逻辑）。
- ⚠️ 两条协议路径都需维护与测试，工程复杂度略增。
- 📌 约束后续：取流层的重连、超时、协议切换策略应可配置，凭证只走 `.env`（不入库）。

## 替代方案（Alternatives）

- **只用 HLS**：否决。切片延迟高，违背低延迟前置预警目标。
- **只用 RTSP、无回退**：否决。部分家庭网络下 RTSP 可能不可用，会造成单点失败。
- **自建拉流转封装（如 WebRTC）**：否决（当前阶段）。属过度设计，MVP 不引入额外流媒体基础设施。
