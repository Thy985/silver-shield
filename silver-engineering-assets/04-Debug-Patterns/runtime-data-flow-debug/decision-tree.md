# Decision Tree · Runtime Data-Flow Debug

> 实时系统「空白 / 无数据 / 状态不对」的分层定位决策树。
> 从最底层（数据产生）往上查，不要从 UI 往下猜。

```
用户看到异常（空白 / 无数据 / 状态跳变）
│
├─ ① 数据是否产生？(Fact)
│   ├─ 查感知层日志 / 输出：有 VisitorEvent / 检测框吗？
│   ├─ 无 → 病根在输入 / 检测（帧源 / 模型 / 解码）
│   └─ 有 ↓
│
├─ ② 事件是否传输？(Pipeline)
│   ├─ 事实 → 特征 → 规则 → 决策，链路每一跳都有产出吗？
│   ├─ 断在某跳 → 规则阈值 / 时间窗口 / 特征缺失（注意时间尺度错配，见 high-not-appearing）
│   └─ 全通 ↓
│
├─ ③ 协议是否收发？(Protocol)
│   ├─ WS / MQTT 帧结构与字段对吗？topic 对吗？
│   ├─ 收不到 → 协议层（序列化 / 订阅 / 连接）
│   └─ 收到 ↓
│
├─ ④ 状态是否保存？(State)
│   ├─ 映射表 / 会话 / 快照 / 循环 / 重置语义对吗？
│   ├─ 闪烁 / 晚连空白 / 多轮崩 / reset 不净 → 状态类缺陷
│   └─ 状态正确 ↓
│
└─ ⑤ 展示是否消费？(UI)
    ├─ 前端读的是正确的状态源吗？（两套状态语义混淆？见 risk-card-false-confirmed）
    └─ 读错源 / 渲染 bug → 才轮到改前端

铁律：在第 N 层定位到病根，就修第 N 层，不要顺手改 UI。
```

## 速查表

| 症状 | 优先查的层 |
|------|-----------|
| 全空白 / 无检测 | ① Fact（帧源 / 模型） |
| 有检测无风险 | ② Pipeline（阈值 / 时间尺度） |
| 连上没数据 | ③ Protocol（WS / MQTT） |
| 状态闪烁 / 晚连空白 / 多轮崩 | ④ State |
| 读到错误状态 / 误显 | ⑤ UI（读错状态源） |
