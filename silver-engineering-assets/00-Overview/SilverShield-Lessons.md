# Silver Shield Lessons（母项目来路）

> 银龄盾（Silver Shield）是如何从一个想法，一步步变成**可验证系统**的。
> 这些是「开发手册」层面的认知；具体的可套用结构见各模式目录。

---

## 一、被验证正确的原则

1. **先事实层，再展示层** —— 展示层的 bug 成本低，事实层的 bug 成本极高；顺序反了用大量返工买单。
2. **冻结边界优于快速修改** —— 核心事实层稳定后冻结契约，上层只经白名单 + 只读消费。银龄盾冻结后展示层剧烈变化，核心一行没动。
3. **E2E 优于单元测试** —— 单测全绿只证明零件对；真实 E2E（网关→WS→状态回写）一次暴露 3 个集成级缺陷。
4. **Demo 是第一个产品入口** —— 不是网页。需真实输入 / 生命周期 / 快照 / 会话管理。
5. **评委关心闭环，不关心页面数** —— 发现→确认→处置→闭环，一条故事线胜过十个孤立页面。
6. **稳定核心高风险比新增功能重要** —— 事实层不出 HIGH，上层全是空壳。
7. **系统验证优于功能验证** —— 长时间运行 / 多轮 / 切换 / 晚连 / 重置，才是运行态验证。
8. **真实数据比模型能力重要** —— Mock 隐藏问题，真实数据逼出问题。
9. **先固定故事，再提高泛化** —— Demo 阶段允许对故事过拟合，但须记录过拟合点。
10. **状态是一等公民** —— 跨时间运行后，状态管理优先级超过模型。
11. **每阶段必须产出可验证资产** —— 没有可重复验证证据的阶段 = 未完成。

---

## 二、被证伪的诱惑（下次直接跳过）

- **先堆页面再接数据** → 大量返工。页面可后做，事实必须先在。
- **视频上传 = 项目价值** → 上传只是入口，价值在闭环。
- **多角色 = 多个系统** → 错误。应是单一事实源 + 多视图投影。

## 四、一句话

> **不要先证明系统很强，而要先证明系统是真的；不要先追求泛化，而要先建立一个能够稳定复现、可验证、可闭环的事实系统。**

---

## 五、给下一个项目的建议

1. 立项即抄 `08-ADR-Templates/` 的模板，先把架构边界定下来。
2. 事实层一稳，立刻写 `03-Test-Patterns/e2e-test` 类型的真实 E2E，别等「功能齐全」。
3. 展示层起步就走 `06-Frontend-Patterns/state-driven-dashboard`（Event→State→Render）。
4. 每踩一个坑，第一时间写进 `09-Failure-Cases/`——这是最值钱、也最易被忽略的资产。
